01 / THE WHOLE SYSTEM

Two different kinds of change

New evidence changes records in the database. New software changes the code serving the site. These have different owners and different release paths.

Key terms used in the map
  • VPS: the always-on hosted server, independent of your Mac.
  • Canonical import: the shared validation-and-save path into the authoritative records; workers do not maintain separate live databases.
  • Observation: something received or read from a source. It is not automatically a new job or a verified claim.
  • Receipt: a dated account of a process’s attempts, results, gaps and usage.
  • Evidence brief: the recorded context and supported evidence you review before acting.
  • Deployment: switching the live site to a tested code revision; ordinary record updates do not need one.
AUTOMATIC DATA LOOP

Discover → validate → save → refresh

Scheduled workers read sources, deduplicate and validate findings, then commit through one record service. Reloading the site displays the updated records; no deployment is needed.

ATTENDED SOFTWARE LOOP

Observe → build → test → release → review

the owner directs agent work. Code is tested and pushed to GitHub, then an authorised operator deploys a pinned revision and checks the live result. Pushing alone does not release it.

02 / DATA REFRESH

Two collection paths, one record system

Collection discovers candidates and source observations. It does not by itself make an approach ready or prove that a vacancy remains open.

1DAILY · ~05:30 UTC

Read configured sources

Employer boards, approved Reed/Adzuna feeds, Hacker News, tenders, public contract awards, funding news and Companies House.

Scope and source limits

Only configured adapters and approved keyed sources run. Company registry reads require an evidenced company number; names are not guessed. Awards and funding become company signals, not invented vacancies. This is not a complete market scan.

2CANONICAL IMPORT

Match and retain evidence

Source identifiers and compatible record details prevent duplicate records. Imports keep source observations separate from your edits and workflow choices.

Duplicates, conflicts and closures

Ambiguous cross-source matches stay separate with a possible-match link. Imports preserve edited fields. Explicit source closure can close a source lifecycle; authoritative inventory absence needs two complete observations at least 24 hours apart. Failed or partial scans cannot establish absence. A date passing alone never closes a job.

3LIVE DATABASE

Reload to see changes

The VPS SQLite database holds jobs, people, organisations, links, notes, evidence, receipts and outcomes. The browser reads the committed record view.

What a new observation means

An import may update an existing job rather than create one. “Five observations” does not mean five new jobs. A fresh import date is not a fresh vacancy check. Your local development database is a separate copy and does not serve this site.

ATTENDED INPUT

Record an incoming role or existing interview

Use Add incoming role in Jobs or This week. Preview matches the existing job before you save the actual stage, dates, employer, agency and private source evidence. It never invents a sent application.

Active processes enter focused research through the shared opportunity policy. Private messages and documents remain context, not public verification. Recruiter mail is not monitored automatically.

PARALLEL INPUT · EVERY 15 MINUTES

LinkedIn alert mail follows its own delivery chain

  1. GmailForwards new mail from the exact LinkedIn job-alert sender; originals stay in Gmail.
  2. Cloudflare D1 bufferDurably holds mail until the VPS acknowledges its own stored copy.
  3. VPS private spoolVerifies the hash, stores the original, then acknowledges. Lost acknowledgments replay safely.
  4. Parser → same importerExtracts eligible advert links, deduplicates observations and records failures or quarantine.
Delivery, retry and coverage boundaries

An empty successful poll means the worker ran; it does not prove alerts are arriving. Old Gmail mail is not forwarded retrospectively. Network posts, InMail and recruiter conversations are outside this filter. Retained mail can still be processed after a collection failure. Malformed/quarantined mail needs investigation; bounded stores do not silently evict pending messages.

03 / CODEX RESEARCH

A bounded researcher, not an autonomous operator

At 09:00 and 19:00 London time, the VPS worker uses the existing Codex CLI ChatGPT login. Research maintains opportunity evidence; outgoing message generation is retired. The Mac can be off.

1

Select the maintained set

Active and shortlisted work plus the top ten discovery opportunities. Targets rotate by oldest attempt, with active work first on ties.

What stays outside the queue?

Archived, excluded, skipped, rejected or closed work. Generic company signals alone cannot qualify as direct-work leads. The worker uses the same selection as This week and Jobs; visits never trigger research.

2

Read before making claims

Known public pages and bounded URL discovery provide evidence. Search results are leads; actual retrieved page text supports a confirmation.

What does Codex receive and control?

A small packet of selected work context, relevant career evidence and public excerpts. The scheduled model session has no database-file access, shell tools or record-write tools. It cannot modify code. A separate attended record gateway permits explicitly requested work from the VPS Codex checkout. It returns structured results. It does not use your signed-in browser, retrieve private mail or bypass blocked pages.

3

Validate and save, or withhold

The trusted worker checks identity, quoted evidence, policy and current eligibility before canonical import. Uncertain claims remain gaps.

Why a model answer may add nothing

A plausible statement is not enough. Claims without supporting retrieved text, ambiguous attribution and inferred authority are withheld. Public profile discovery is a route to review, not proof of delivery. New employment evidence cannot overwrite protected fields or silently change your selected channel.

EVIDENCE MAINTENANCE

One work assessment

Combine remit, fit, demand evidence, terms and decisive unknowns. Retain supported quotations, source URLs and read dates. A source may support an advert, a specific direct-work remit or an exact contact route.

Generated wording is never independent evidence. Unsupported claims stay unknown.

REUSE AND PRESERVATION

Reuse evidence; keep history

Current evidence and unchanged context avoid unnecessary calls. Research does not generate messages or create draft approvals. Old pending preparation batches cannot restart that workflow.

Saved draft versions, sent wording, decisions and outcomes remain available through read-only history, export and restore. Composition belongs in Gmail.

Freshness belongs to a specific claim

CONFIRMED <24 HOURS

A source observation supports that exact vacancy or route. A profile confirmation does not establish hiring authority, message delivery or willingness to help.

OLDER THAN 24 HOURS

Needs rechecking. A new email, record edit or cached interpretation cannot reset the actual source-read timestamp.

BLOCKED / UNVERIFIED

A later failed public check can supersede an earlier public confirmation. The owner-confirmed routes and prior-correspondence evidence retain their separate provenance.

Allowance, cache, interruption and replay

Research permits at most six CLI invocations per pass, 12 per London day and 84 per Monday-start week. At most thirty targets are assessed per pass. Calls are reserved durably before dispatch; failed, timed-out and uncertain attempts count. These count invocations, not account-wide credits. There is no API-key fallback.

Confirmed checks younger than eight hours need no new read. A validated interpretation can be reused for seven days only with fresh matching source text, unchanged context and policy. Failed reads have a 24-hour cooldown; discovery is cached for seven days. None of this extends freshness without evidence.

Immutable batches are stored before import. Recovery replays through the same validation and deduplication without another model call. Missing batches after a database-only restore remain visible. Restoring an old usage ledger does not restore account allowance; accounting reconciliation is an attended recovery step.

What useful output should you expect—and measure?
  • A decision-changing fact: an open advert, a specific remit, location constraint, terms or essential skill gap.
  • Supported context: an attributable current role or exact public source worth reviewing.
  • An honest stop: missing evidence that prevents pursuing unsuitable or unsupported work.

Measure worthwhile opportunities identified and decisions made more easily. A pass can produce no new facts; a technical pass does not prove usefulness.

04 / THE HUMAN LOOP

Evidence becomes useful when you act

This week shows actionable work in progress and ranked discovery. Suitability and evidence date lead; engagement preference breaks ties. Best opportunities starts with three cards and expands to ten. Unknown terms stay explicit.

  1. Choose worthwhile work

    Review the assessment and its decisive unknowns. Jobs owns the complete lifecycle; old Pipeline links redirect there.

  2. Retrieve relationship context

    People holds relationships, contact/reply history and optional recorded next steps. Personal outreach is yours to manage.

  3. Compose and send in Gmail

    Use your own wording and tools, or apply through the source site. There is no site email-copying workflow.

  4. Optionally record what happened

    Record factual contact, reply or next step. Shared progress controls retain failed edits and support Undo; historical wording remains read-only.

There are no personal outreach quotas or automatic personal follow-ups. The site does not read replies from your mailbox.

05 / OPERATIONS & RECOVERY

Detect problems, preserve evidence, recover with an operator

CARETAKER · EVERY 15 MINUTES

Observe → receipt → visible incident

Deterministic checks inspect fixed services and timers, site health, processing receipts, mail/backlog capacity, source outcomes and backup evidence. The caretaker makes zero model calls.

What do its states prove?

Healthy means that particular check has evidence. A recent completed research pass can clear its execution incident even with unverified routes: an ok receipt, or partial with no stop reason. Source gaps remain visible. Other partial checks, waiting, paused and unknown states do not clear a failure. Stable incident identities avoid duplicate decisions. The caretaker never restarts a service, retries a model request, repairs data or deploys code.

Jobs leave short failure notes for the caretaker to include on cards. Three crashes in 24 hours raise a separate service incident even after a successful run. That incident clears once the count falls below three. Use /caretaker in an attended coding chat to investigate within its access limits.

It runs on the VPS it checks. If that server is down, it cannot publish an incident. An already-open page marks the last receipt Overdue after 45 minutes. The email/ingest/backup watch raises a caretaker incident after two hours, provided those jobs and the database still work. There is no independent uptime monitor or external push-alert service.

BACKUPS · SNAPSHOTS

VPS archive → Mac database copy

Nightly at 02:15 UTC the VPS creates encrypted database and separate mail/state snapshots. Those archives are on the same VPS. At 07:30 Mac-local time the Mac copies the site database archive and tests its restore.

What recovery still depends on

The Mac must be available for the off-host copy. Mail spool/state and raw research batches remain on the VPS; Gmail originals provide independent mail evidence. D1 retains only unacknowledged mail, not a complete archive. Backups are not continuous replication or a zero-loss guarantee.

Recovery needs an operator to inspect the relevant receipt, restore or replay safely, reconcile accounting where necessary and verify the actual result. The VPS caretaker cannot verify the Mac’s off-host restore drill.

Access, credentials and the live-data boundary

Browser/phone → Cloudflare Access (one-time PIN, one-week session) → outbound Tunnel → loopback-only VPS application. The origin validates the Access token. These diagrams remain inside the same private site; they add no public access.

Service credentials are systemd-encrypted and scoped to their workers. The web process cannot read them. The live SQLite file itself is not application-encrypted. Agents read or edit live records through the approved ops/wo-live gateway; a development copy is never the live database. The restricted attended VPS route has no server shell, file/backup reads or deployment access. It is separate from the scheduled research model session. Code and docs are in private GitHub; raw mail, credentials and live personal exports are outside Git.

06 / SOFTWARE IMPROVEMENT

A complete attended release path

Monitoring and research supply evidence for improvements. They do not launch a software engineer or release changes automatically.

  1. Evidence → direction

    the owner identifies the objective using experience, records or failures. An attended agent investigates and implements within that request.

  2. Tests → main

    Validate code, HTTP behavior and browser flows on synthetic fixtures. Push the reviewed changes to the configured main branch.

  3. Authority → deployment

    Use /deploy from an authorized operator environment to request a release. Dry-run the deploy, pass strict checks, then the VPS fetches the pinned pushed revision. Migration and timer changes stay explicit.

  4. Hosted checks → usefulness

    Verify serving revision and hosted behavior. Observe real scheduled runs separately. The owner assesses whether the change saves time or improves decisions.

Not implemented: autonomous self-improvement. There is no scheduled Codex incident-diagnosis worker, weekly software-improvement reviewer, automatic code repair, commit/push or deployment. Reserved allowance categories are not running capabilities. The VPS GitHub key is read-only.
If a release or operational fix fails

Keep the failure evidence and investigate in an attended session. A passing test or repair note does not establish recovery. Verify the affected source or service after the fix. Code rollback must be compatible with the database schema and use the normal authorised deployment path.

How long before status becomes overdue?

Receipt thresholds: email 45 minutes; research 16 hours; daily collection and nightly backup 30 hours; caretaker 45 minutes. These are operational deadlines, separate from 24-hour source-check freshness. Active bounded runs and usage waits have their own states and do not prove complete coverage.
